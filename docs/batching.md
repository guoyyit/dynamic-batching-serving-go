# 批处理语义

本文档固化“请求如何合并成批、批次如何拆分执行、结果如何返还”的确定性规则。
所有规则均由代码实现并由测试锁定（`serving_test.go`、`retry_test.go` 等）。

## 1. 基本对象

- `Request{Model, Payload}`：一次推理请求，`Payload` 对调度器不透明。
- `enqueued`：队列条目，携带容量为 1 的结果通道 `done`。
  结果通过 `settle(sync.Once)` **恰好写入一次**。
- `batch`：一个已出发的混合批次，含一个或多个 `batchGroup`。
- `batchGroup`：发往**同一模型**的子批，成员来自同一 FIFO，并固化了
  组批时刻的 `RetryStrategy/MaxRetries` 与来源队列引用。

## 2. 合并（组批）规则

调度循环以 `min(TickInterval, 1ms)` 的节拍运行，提交动作与回队重试会
通过 `wake()` 立即触发一次检查（深度触发不靠轮询）。

每个节拍，对**全部模型**做处理，顺序与规则如下：

1. **失效清理（阶段 0）**：对每个模型，从队首取出连续的
   “已超时 / 已取消”条目，立即结算并移出队列，腾出槽位。
   这些请求**不会**进入任何批次（满足“不得被塞进已经出发的批次”）。
2. **触发判定（只窥视，不出队）**：模型按**名称字典序**遍历，
   对每个非空队列判定是否应在本拍出发：
   - **深度触发**：队列深度 `>= MaxBatchSize`；
   - **窗口触发**：队首请求的等待时间 `>= BatchWindow`。
   任一模型命中即标记本拍需要出发；未命中的模型本拍完全不动
   （不会“取出又放回”，避免抖动与饥饿）。
3. **真正出队**：只对命中触发的模型，从队首取至多
   `min(MaxBatchSize, 剩余在途名额)` 个条目；再次过滤其中已
   超时/取消的条目（结算、不进批），其余构成子批。
4. **混合成批**：各模型子批仍按**模型名字典序**组成一个 `batch`，
   并记录出发时的**配置版本号** `batch.version`。

因此：

- 同一批可以混合不同模型，但每个子批的 `MaxBatchSize/BatchWindow/
  重试策略` 都来自该模型**当前且同一**配置版本；
- 模型顺序、批内顺序都是确定的（字典序 + FIFO），结果可复现；
- 一个请求在任一时刻只存在于“队列”或“某一个批次（含回队重试）”中，
  由容量记账 `len(items)+outstanding <= QueueCapacity` 保证不重复。

### 窗口与深度如何兼顾延迟与吞吐

- 低负载：请求等满 `BatchWindow` 即走，单请求延迟上限≈窗口；
- 高负载：队列很快达到 `MaxBatchSize`，立即出发，不被窗口拖慢；
- 批大小分布（`Stats().Models[i].BatchSizeDist`）可直接观测这一行为。

## 3. 拆分（执行）规则

工作协程从固定容量的批次通道取批，按组依次调用 `Inferencer`：

1. 按 `groups` 顺序（模型名字典序）逐组执行；**组与组之间互不影响**，
   一个模型的失败不会丢失其他模型的结果。
2. 每次调用 `Infer(ctx, model, payloads)` 前，会先剔除在途期间
   已超时/取消的成员（它们不被送入引擎，直接结算）。
3. 引擎契约：
   - 返回 `results` 与 `payloads` **等长且下标对齐**：单项失败用
     `results[i].Err` 表达（部分失败），其余下标结果照常；
   - 无法逐项给出结果时返回非 nil 的整批错误。
4. **结果按下标精确返还**给原请求通道；不存在跨模型、跨下标的错配。
   下标对不齐被视为引擎违约，整批按不可重试失败确定性结算。

## 4. 失败与重试（不产生重复副作用）

- 不可重试错误：该单项立即以 `failed` 结算；同批其他项不受影响。
- 可重试错误且策略允许：
  - `immediate`：在**本次执行循环内**只对失败成员再次调用 `Infer`，
    上限 `MaxRetries`；超过以 `retry_exhausted` 结算。
  - `requeue`：失败成员按原顺序放回所属模型**队首**，由后续批次处理，
    跨批次的总尝试次数仍为 `MaxRetries+1`。
- **关键不变量：成功的成员永远不会被再次送入 `Infer`。**
  无论整批错误还是单项错误，重发集合只包含“尚未成功”的成员，
  因此重试不会对成功操作重复产生副作用。
- `never` 策略下即使引擎返回可重试错误也不重试，按 `failed` 结算。

## 5. 超时 / 取消在批处理各阶段的结论

| 阶段 | 行为 |
| --- | --- |
| 等待队列槽位（block 背压） | 超时→`queue_timeout`，调用方取消→`canceled` |
| 在队列中等待组批 | 调度循环每拍清理队首失效请求，结论同上，**不进批** |
| 已出队、批次尚未执行 | 工作协程执行前再检查一次，失效项不调用引擎并结算 |
| 正在 `Infer` 中 | 等待引擎返回；若引擎尊重 ctx 可提前返回可重试错误；返回后仍正常结算 |
| 已成功执行 | 结果已写入容量 1 的通道，随后的 ctx 取消不会使其丢失 |

超时优先于取消判定，二者通过不同 `Reason` 稳定区分。
